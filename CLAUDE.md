# Qintar — instructions for AI contributors

Qintar is an offline Android app that counts the Quran ayahs a user reads per day and ranks the day
on a seven-step ladder from a hadith. The design is specified in `docs/v2/DESIGN.md`. Read the
sections a task touches before a non-trivial change (grep its headings; it is long); it is the
source of truth and its "Decision" sections are not to be reopened without the owner.

## Invariants (breaking one of these is a bug, whatever the task)
- All counts derive from `read_event` and `read_tally`. Never store a derived count, rank or streak.
- Only `ReadingTracker` (and `ReadingLogImporter` for backups and the v1 carry-over) writes reading records.
- Time comes from `DayClock`. Never call `LocalDate.now()`, `Instant.now()` or
  `System.currentTimeMillis()` elsewhere. Never hold a "today" value across a suspension without
  observing `todayFlow`.
- No destructive database fallback. Every schema change has a migration and a migration test.
- Quran text is never modified. Formatting happens at display time. The bundled `quran.db` asset is
  generated by `tools/quran-data` and must be reproducible (CI checks it).
- `:domain` has no Android imports.
- UI uses design-system tokens and components only (`ui/designsystem`): no literal colours, sizes,
  fonts or strings.
- Every user-visible string exists in `values`, `values-fa` and `values-ar`. Arabic uses ي ك;
  Persian uses ی ک. Counts use plurals.
- Layouts are start/end based; nothing assumes left-to-right.
- The v1 user database (`databases/quran_bookmarks_database`) is only ever read, and deleted only
  when the user asks for it in Settings.

## Modules
- `:domain` — pure Kotlin/JVM: models, ports (`domain/port/Ports.kt`), services (tracker, ranks,
  streaks, khatm, bookmarks, insights, reminders planning), backup format and the v1 converter.
  Test fixtures (`DomainFixture`, fakes) live in `domain/src/testFixtures`.
- `:data` — Android library: Room user database `qintar.db`, the read-only Quran database
  `quran-text.db` (copied from the `quran.db` asset), preferences DataStore, backup JSON codec,
  v1 reader/migrator/leftover files, Hilt `DataModule`.
- `:app` — Compose UI by feature (`feature/*`), design system (`ui/designsystem`), navigation
  (`ui/navigation`), Media3 playback (`playback`), reminders (`reminders`), Hilt wiring.

## Environment (Linux / WSL)
Java 17 and the Android SDK are needed. Either `source ~/tools/qintar-env.sh`, or prefix commands with
`export JAVA_HOME=$HOME/tools/jdk-17.0.21+9 ANDROID_HOME=$HOME/Android/Sdk;`.

Redirect long Gradle output to a file and read the tail or grep it; do not paste it whole.

## Commands
- All unit tests: `./gradlew :domain:test :data:testDebugUnitTest :app:testDebugUnitTest`
  (`:data` and `:app` tests run on Robolectric; no device needed).
- Screenshots (Roborazzi, light/dark × en/fa): `./gradlew :app:verifyRoborazziDebug`; after an
  intended UI change, `./gradlew :app:recordRoborazziDebug`, look at the changed PNGs under
  `app/src/test/screenshots/`, and commit them.
- Lint: `./gradlew :app:lintDebug`
- Build: `./gradlew :app:assembleDebug :app:assembleRelease` (release is unsigned without the
  signing variables, see `docs/v2/RELEASING.md`).
- Quran data reproducibility: `python3 -I tools/quran-data/build_quran_db.py --check`

## Running on a device or emulator
The debug build is `io.github.mehrdad_abdi.quranbookmarks.debug` and installs next to a release.
Under WSL with the emulator running on Windows, use the Windows `adb.exe`
(`/mnt/c/Users/<you>/AppData/Local/Android/Sdk/platform-tools/adb.exe`); it cannot read WSL paths,
so copy the APK to a Windows folder first and install it from its `C:\...` path.
`adb exec-out screencap -p > shot.png` and `adb shell uiautomator dump` help to drive and check
screens. A device's own data is the user's: never uninstall the app or clear its data without being asked.

To test the in-place upgrade from v1, build with `-Pqintar.v1UpgradeTest=true` (debug build without
the `.debug` suffix) and install it over a debug build of tag `v1-final`.

## Workflow
1. Find the requirement IDs (R-…) the task serves; if none fits, ask the owner.
2. Write or update tests in the same change (DESIGN.md §8).
3. Run the unit tests, lint, and the screenshot check if UI changed; build.
4. Bump `versionCode` for anything that will be released. Summarise what changed, what was
   verified, and what was not.

## When unsure
Prefer the simpler mechanism already in the codebase over a new one. If a rule in the design
document seems wrong for a case it did not foresee, stop and ask rather than working around it.
